# Magnet Sort — GDD v0.3

Дата: 2026-10-09. Актуальное направление: настоящее 3D на Three.js, магнитное притяжение и поштучный перенос между соседними hex-клетками. Этот документ заменяет конфликтующие решения GDD v0.1/v0.2, RULES v1–2 и PIXI_RENDERING. Исторические документы сохранены для старой сборки, а не как требования нового прототипа.

## 1. Суть игры

Игрок выбирает цветной магнит и ставит его в пустую клетку. Магнит притягивает открытые элементы своего цвета. Стопка разбирается сверху: каждый элемент быстро перелетает с переворотом в соседнюю клетку и ложится поверх принимающей стопки. Цепочка таких переносов доставляет элементы к магниту, освобождает места и открывает нижние цвета.

Главное удовольствие — предсказать цепочку и запустить её одним размещением. Игрок не добавляет стопки, не перемещает их вручную и не управляет отдельными элементами. Стопки уже расставлены автором уровня.

Цель прототипа — очистить поле за ограниченное число размещений магнита. Три коротких поля должны проверить понятность притяжения, темп поштучного движения и интерес смешанных стопок до расширения кампании.

## 4. Поле, стопка и магнит

- Геометрия — odd-r hex-сетка с прежними стабильными ID `r{row}c{col}`. Уровень явно задаёт существующие клетки: первый прототип использует 5×5 внутри координат 1…5 прежней сетки 7×7. Отсутствующая клетка непроходима.
- Клетка содержит одну стопку либо блокер либо пуста. В стопке — массив отдельных элементов снизу вверх, у каждого уникальный ID и цвет. Число видимых слоёв совпадает с фактическим числом элементов; прежний декоративный cap из шести слоёв не применяется.
- Смешанная стопка хранит реальные нижние цвета. Двигается только непрерывный верхний слой выбранного цвета. Элемент под другим цветом неподвижен.
- Магниты: фиолетовый, голубой, коралловый, без декоративных символов по выбранной редакции мокапов. Названия цветов доступны в aria-label кнопок. Первое поле предлагает один цвет, следующие — три. Магнит выбирается из DOM-панели; случайного tray со стопками нет.
- Поставить магнит можно только в существующую пустую незаблокированную клетку. Магнит не расходует элемент, не добавляет массу и не является постоянным блокером.
- Во время разрешения в клетке магнита виден 3D-маркер; элементы могут собираться над ним. После полного разрешения магнит исчезает, остаточная стопка остаётся.

## 5. Исполнимые правила притяжения — rulesVersion 3

1. Контроллер принимает `placeMagnet { color, cell }` только в фазе playing. Неверная клетка, недоступный цвет, пауза, resolving или terminal не создают ход.
2. Для выбранного цвета строятся расстояния BFS от магнита. Блокеры, отсутствующие клетки и стопки с несовместимым верхним цветом закрыты. Пустая клетка и стопка с верхом выбранного цвета проходимы. Дальность — весь связный доступный участок поля.
3. Из доступных стопок выбранного цвета, кроме самой клетки магнита, выбирается ближайшая по найденному расстоянию. При равенстве: row, затем col. Следующая клетка — сосед с расстоянием на единицу меньше. Равные пути разрешаются порядком hex-направлений `(1,0), (1,-1), (0,-1), (-1,0), (-1,1), (0,1)` в axial-координатах.
4. Выбранная стопка отдаёт в эту соседнюю клетку верхние элементы выбранного цвета по одному до появления другого цвета или опустошения. Каждое событие содержит ID элемента, обе клетки и индексы высоты. Нельзя переместить стопку целиком, перепрыгнуть клетку, пересечь блокер или переложить элемент на несовместимый верх.
5. В клетке магнита каждые ровно 6 накопленных элементов выбранного цвета очищаются. Неполная группа не исчезает. Промежуточные стопки автоматически не очищаются и не сливаются удалённой компонентой. После очистки текущий поток может продолжиться.
6. После переноса верхнего слоя маршруты вычисляются заново: мог открыться новый цвет или освободиться проход. Цикл повторяется, пока нет доступной подходящей стопки. Недостижимые элементы остаются на месте.
7. Принятое размещение расходует один ход даже без переноса. В конце проверяется победа: на поле нет элементов. Затем поражение: закончились ходы или нет пустой клетки. Победа на последнем ходе имеет приоритет. Если остались только заблокированные цвета, игрок может сменить магнит; автоматического solver для определения тупика нет.

Масса сохраняется: `remaining + cleared = initial`. ID элемента неизменен через все соседние шаги до его очистки. Модель синхронно рассчитывает state и события; view воспроизводит их, не решает правила. Порядок исходного массива стопок, FPS и reduced motion не изменяют результат.

Магнитное притяжение — управляемое дискретное поведение. Постоянных магнитов, взаимодействия нескольких магнитов, полюсов, отталкивания и physics engine в этом срезе нет.

## 6. Движение и обратная связь

- Для каждого переноса соседнего верхнего слоя создаётся последовательность отдельных полётов. Следующий элемент стартует, пока предыдущий ещё летит: поток выглядит быстрым и плотным.
- Элемент уходит с фактической высоты вершины источника; целевая высота учитывает уже отправленные элементы. Источник уменьшается сверху, приёмник растёт по одному слою. Ни дублирования массы, ни заранее собранной конечной стопки.
- Обычный профиль: 190 мс полёт, 55 мс между запусками, дуга до 0.54 world unit, один переворот 360° вокруг горизонтальной оси поперёк направления движения. Это исходная настройка нашего прототипа для дальнейшей оценки пользователем.
- После посадки последнего элемента данного переноса начинается следующий соседний перенос. Элемент не перелетает через несколько клеток одним tween.
- Очистка начинается после посадки группы и занимает 220 мс. Счётчик очищенных элементов обновляется после её завершения, результат появляется после последней анимации всего хода.
- Reduced motion: полёт 90 мс, интервал 45 мс, без дуги и вращения; события, порядок и конечное состояние сохраняются. Во время цепочки ввод заблокирован.
- Pause/blur/hidden замораживают presentation time и отменяют жест. Resume продолжает цепочку; reset/смена уровня отменяют её полностью. Старый callback не может вернуть отменённый результат.
- Отдельный звуковой профиль и haptics отложены до оценки движения. Старые MVP-cues нельзя автоматически объявить соответствующими этому видео.

## 7. 3D и визуальная композиция

Настоящие mesh-элементы на Three.js: hex-плитки с толщиной, стопки из отдельных объёмных колец, 3D-магнит, материалы, освещение, глубина и тени. Фиксированная наклонная OrthographicCamera оставляет размеры клеток понятными. Свободное вращение камеры не требуется для основной механики.

Тема прототипа: яркий фиолетово-синий hex-фон, светлые панели с золотистой кромкой, керамические клетки и глянцевые цветные кольца. HUD над полем, магниты и действия под ним; на коротком landscape controls справа. Все видимые тексты — английские. Символы с магнитов и колец убраны; выбранный инструмент выделен рамкой. Цветовые aria-label сохранены, отдельный визуальный режим для нарушений цветовосприятия пока не реализован. [План переноса](CASUAL_MIGRATION.md), [отчёт](../reports/CASUAL_DESIGN.md).

Касание/мышь: выбор цвета → тап пустой клетки либо drag магнита из панели. Наведение показывает допустимость клетки и магнит. Клавиатура: кнопка цвета → focus canvas → стрелки → Enter/Space; подсказка выделяет авторскую клетку и объясняет координаты. Доступные DOM controls и live-status сопровождают canvas.

## 8. Три поля прототипа

| Поле | Проверяемая идея | Содержание |
| --- | --- | --- |
| Первое притяжение | Одно действие запускает длинную цепочку | 12 фиолетовых элементов, 3 размещения; решение за 1 |
| У каждого цвета своя сила | Выбор цвета и обход блокера | 18 элементов трёх цветов, 1 блокер, 4 размещения; решение за 3 |
| Под верхним слоем | Открытие нижнего цвета и сохранение неполной группы | 3 смешанные стопки, 18 элементов, 2 блокера, 5 размещений; решение за 4 |

У каждого поля сохранено авторское решение. Подсказка доступна только при точном совпадении текущего состояния с префиксом этого решения; на другом состоянии она не выдаёт произвольный якобы выигрышный ход. После третьего поля можно начать цикл сначала. При поражении — повтор того же поля.

## 9. Технология и переход

- Текущий entry `src/main.js` запускает только `src/prototype/runtime.js`. Three.js зафиксирован в package.json/lockfile; Preact сохраняется. Точный rendering/lifecycle контракт: [THREE_RENDERING.md](THREE_RENDERING.md).
- Чистая модель v3 и ordered elements отделены от legacy `mass` model. Старые 50 уровней, сохранения, daily/challenge, скоринг, реклама и платформенные adapters остаются исходниками прежнего MVP; в новом прототипе не используются и не записываются поверх прежнего progress.
- PixiJS временно остаётся зависимостью для исторических модулей и их регрессионных тестов, но не входит в import graph новой игры. Удалять legacy-код и зависимость следует отдельным осознанным шагом после решения о переносе контента.
- Один app-owned RAF работает только во время анимации. Чистая симуляция хода не зависит от frame time. Изменение размера и hover вызывают render по событию. Shared geometry/material переиспользуются; reset не создаёт новый renderer. Dispose освобождает GPU-ресурсы, shadow target, listeners, ResizeObserver и RAF.

Дальнейший порядок: оценка текущего движения пользователем → настройка силы/правил и небольших puzzles → перевод выбранного контента на v3 → новый scoring/save namespace → по отдельной необходимости social/daily/платформа. Старые отчёты MVP не принимают новую версию автоматически.

## 10. Критерии прототипа и границы evidence

- В браузере виден настоящий 3D-board; runtime не запускает Pixi Application.
- По tap и drag размещается магнит; каждый видимый элемент пересекает одну соседнюю грань за перенос. Несколько элементов одной последовательности могут быть в полёте одновременно.
- Смешанный стек показывает реальные нижние цвета; закрытые элементы неподвижны. Очистка сохраняет остатки и массу.
- Все авторские решения заканчиваются победой; последние ходы, ошибочные клетки, no-effect placement и поражение проверены моделью.
- Ввод блокируется во время resolve; reset посреди полёта, pause/resume, blur/hidden, resize, reduced motion и dispose не дают зависших элементов, лишних ходов или renderer.
- Desktop и mobile viewport проверяются в браузере с кадрами, отдельно от реального телефона. Обязательные команды: `node --test tests/prototype-v3.test.js`, `pnpm check:full`, `pnpm test:browser` при работающем dev server.

Целевой физический baseline остаётся Pixel 6a / Android 13+ / Chrome с целью p95 frame <16.7 мс при 60 Hz. Это цель, не результат. DPR ≤2 и shadow map 1024 — текущие настройки прототипа, не доказательство мобильной производительности. Физический телефон и внешняя оценка ощущения не проверяются эмуляцией. Отчёт реализации: [THREE_PROTOTYPE.md](../reports/THREE_PROTOTYPE.md).

Прототип не является переносом всей прежней кампании и платформенной игры. Публикация, приглашения, Telegram, монетизация и отправка сообщений другим людям не входят в запрос.
