Это направление визуального оформления; правила, scoring и экономика не менялись.

[HEXA_STACK_REFERENCE](../reports/HEXA_STACK_REFERENCE.md) и [отчёт выполнения TASK-0023](../reports/HEXA_STACK_VISUAL.md).

## Актуальное решение: PixiJS и псевдо‑2.5D (GDD v0.2, 2026-10-07)

- Пользователь после сравнения вариантов выбрал вернуть PixiJS и псевдо‑2.5D. Это согласуется с исходным GDD v0.1. Мягкий toy-like объём создают 2D-слои, фаски, блики, тени и анимации; настоящая 3D-сцена не входит в MVP.
- GDD v0.2 задаёт PixiJS 8 pseudo‑2.5D; grid simulation остаётся детерминированной и без физического движка. HUD остаётся DOM/Preact. Подробности: `GDD_V0.2.md` и `PIXI_RENDERING.md`.
- Завершённые TASK-0003/0004 и текущая сборка уже используют нужный PixiJS renderer. TASK-0023 отменена/удалена; TASK-0005 продолжает очередь после физической touch-проверки.
- Из общего чата использованы Magic Sort 27, Water Sort Master, Hexa Color Sorting Puzzle и авторский концепт. Из списка GDD v0.1 использованы Hexa Sort, Hexa Stack, Water Sort и Magic Swap Puzzle. Визуальные и UX-паттерны — направления изучения, не копирование ассетов и не свидетельство renderer технологии.
- Снимок Instant Intel от 2026-10-07: AHA 17M MAU, Magic Swap Puzzle 12M, WOW 7.9M, 8 Ball Pool 6.1M; карточка Magic Swap обозначает его #1 в Casual-Puzzle. Это сторонняя динамическая оценка, а не подтверждённая официальная аналитика Meta.

Подготовлено 2026-10-07. Документ объясняет границы заданий; это не выполненная спецификация игры. Статусы и отчёты находятся в `docs/tasks/`.

## Что сохранилось из диалога

Пользователь попросил упростить первоначальный physics/social концепт. Итоговое направление: одна понятная операция с магнитом, много видимых последствий, hex-сортировка и вызов другу на точно том же поле. Предложения про Chaos Duel, другие игры, общий движок для нескольких продуктов и SORT IT! как расширяемую коллекцию механик не входят в текущую игру. Рабочее название остаётся Magnet Sort.

Визуальные схемы встроены в DOCX: светлое поле 7×7, мягкие hex-фишки, отдельный tray, score и заметный friend challenge. Все три встроенных изображения просмотрены. Они концептуальные: схема pull показывает несовпадающие цвета и не определяет правило симуляции. Изображения дают визуальное направление, текст RULES должен определять механику. Для автономного чтения задач сохранены [board](references/board.png), [sequence](references/sequence.png), [challenge](references/challenge.png). Использовать как внутренние референсы, не как готовые игровые ассеты или подтверждение лицензий чужих материалов.

## Предлагаемые границы интерфейсов

Ниже ориентиры для TASK-0001, а не уже существующий API:

- `LevelDefinition`: puzzleId, seed, contentVersion, rulesVersion, board geometry, colors, initial tokens с ID/color/mass/cell, blockers, goal, moveLimit, magnet schedule/options, solution fixture metadata.
- `Action`: выбранный доступный цвет и целевая пустая клетка; вспомогательные действия имеют отдельный тип и assisted policy.
- `GameState`: tokens/blockers, turn/moves, доступность магнитов, progress цели, terminal state, deterministic counters. Удалённые токены учитываются отдельно для clear %.
- `applyAction(state, action)` → принятая/отклонённая команда, новая state, упорядоченные move/merge/clear/goal/result events. Функция не знает UI, анимации, network или wall-clock.
- `RunResult`: puzzle/version/mode, score/moves/clear %, active time, win/loss, assisted flags, comparison policy version. Нельзя случайно сравнивать разные rules/content.
- Presentation получает state/events и проигрывает эффекты; session владеет фазами и input gate; Preact не повторяет игровые правила; SDK/analytics — adapters с обработкой ошибок.

Существующие `createStepper`, `createScene`, `createInput` и dev `gameDebug` — проверенные точки входа. Будущие файлы в заданиях помечены допустимыми новыми файлами; исполнитель обязан сверить актуальный код после выполнения зависимостей.

## Готовность и внешние условия

TASK-0001 и TASK-0019 имеют ready: это ограниченные задачи определения контрактов/исследования. Остальные draft, поскольку зависимости ещё не выполнены. Будущая задача готова только после проверки отчётов и актуального кода, а не после простого изменения INDEX.

Для prototype gate нужны новые тестеры и реальное устройство; если их нет, подготовить протокол, не выдумывать evidence. Для платформенных функций нужны выбранный Meta app, dev access и реальный test context/ads placement. Не хранить секреты в docs. Для production analytics ещё нужен выбор collector; до этого допустим только явно локальный adapter и честное ограничение.

Текущая папка является Git-репозиторием на `main`, `origin` настроен на адрес пользователя; checkout пока без начального коммита и remote не содержит веток. Это ограничение синхронизации, не часть продуктового дизайна.

Критерии разработки не равны метрикам успеха: FTUE >80%, completion >60%, retry >35%, challenge created >10% и open-to-play >35% в GDD — гипотезы для реальной выборки. Тесты проверяют события и игровое поведение, не гарантируют эти проценты.

Post-MVP: portals 51+, Reverse/Twin и прочие механики, косметика/ASMR, meta/коллекции, аккаунты, UGC, real-time multiplayer. Публикация и Telegram не входят ни в одно подготовленное задание.
