# Magnet Sort — правила модели, v1–v2

Статус: авторская исполнимая трактовка GDD v0.1 для прототипа и кампании. Она снимает неоднозначности, но ещё не подтверждена игровым тестом. Изменение семантики требует увеличения `rulesVersion`; сохранённые challenge/results с другой версией нельзя сравнивать.

## 1. Поле и координаты

- Поле — 7 строк × 7 столбцов odd-r offset. Каждая пара `col,row` в диапазоне 0…6 — существующая клетка; `blockedCells` сохраняют координату, но недоступны для токенов и магнита. За краем поля клеток нет.
- Offset → axial: `q = col - floor(row / 2)`, `r = row`. Обратно: `col = q + floor(r / 2)`, `row = r`. Стабильный ID клетки: `r{row}c{col}`. Порядок сериализации: row, затем col.
- Axial направления в порядке обхода: `(1,0), (1,-1), (0,-1), (-1,0), (-1,1), (0,1)`. Соседи за границей исключаются. Hex distance: `(abs(dq) + abs(dr) + abs(dq+dr))/2`.
- Кратчайший маршрут строится BFS по клеткам поля; blockers и ящики закрыты, токены игнорируются при выборе геометрического маршрута. Среди равных вариантов берётся первый достижимый следующий шаг согласно порядку направлений выше. Токен не телепортируется через занятые клетки.

## 2. Ход, магнит и притяжение

- `Action` выбирает доступный на этом ходу цвет магнита и пустую, не заблокированную целевую клетку. Вход проверяется целиком до изменения state. Невалидное действие возвращает причину, не меняет state и не расходует ход.
- Магнит временный: его координата служит целью только для текущего действия и не занимает клетку после разрешения. Токен может закончить движение на клетке магнита.
- За ход выбирается один цвет. Если уровень предлагает несколько цветов (с уровня 21), игрок выбирает ровно один. Список выбора детерминированно задан расписанием уровня; скрытого RNG нет.
- Притяжение идёт одновременными дискретными волнами. В каждой волне каждый подвижный токен выбранного цвета делает не более одного шага по кратчайшему доступному маршруту к магниту. Волны повторяются до покоя. Это авторское уточнение GDD: одиночный шаг конфликтовал с обещанной цепью.
- Валидное действие всегда выполняет хотя бы один resolve pass, даже если ни один токен выбранного цвета не может сдвинуться; это позволяет объединить уже соприкасающиеся компоненты. После последней волны движение прекращается, но слияние/clear данной волны завершается перед проверкой покоя.
- На волну сначала фиксируется снимок занятости. Токен может перейти только в клетку, свободную в начале волны; цветные токены блокируют клетку назначения независимо от цвета. Токены не меняются местами и не проходят сквозь занятые клетки. После слияния/очистки начинается новая волна с новым снимком.
- Если несколько токенов претендуют на одну пустую клетку, приоритет: меньшее расстояние до магнита, затем меньший стабильный `tokenId` (Unicode code point order). Только победитель перемещается; остальные остаются. Перестановка массивов входного JSON не меняет результат.
- Недостижимые из-за blockers токены, токены на магните и токены без свободного шага остаются на месте. Токены других цветов не двигаются; после clear клетка свободна для следующих волн выбранного цвета.
- Для защиты от бесконечной цепи расстояние любого перемещённого токена строго уменьшается. Счётчик волн ограничен числом клеток поля + 1; превышение считается нарушением инварианта уровня и даёт диагностическую ошибку, а не дополнительный ход.

## 3. Слияние и очистка

- После каждой волны рассматриваются компоненты связанных стороной токенов одного цвета. Связь — соседство hex-клеток, не диагональная близость в прямоугольной записи.
- Компонента с суммарной массой меньше 3 не меняется. При массе 3 или больше она становится одним стеком с массой, равной сумме масс, в клетке токена с лексикографически минимальным `tokenId`. Это правило одинаково для компонент из 3, 4, 5 и 6+ единиц. Мини-стек массой 2 даёт две единицы порога.
- Любой завершённый стек массой 5+ сразу очищается: token удаляется, его полная масса добавляется к `clearedMass`. Поэтому масса 4 остаётся стеком 4; 3+2 даёт clear массы 5; масса не теряется при merge.
- Все компоненты одной волны разрешаются из одного снимка после движения; компоненты обрабатываются в порядке минимального `tokenId`. Слияние не может менять соседство другой компоненты в той же фазе.
- После merge/clear повторяется притяжение выбранного цвета. Другие цвета не сливаются задним числом в этом же ходе. Chain — число последовательных волн, в которых очистился хотя бы один стек; несколько очищенных стеков за одну волну дают один chain-link.
- Цель проверяется по `clearedMass`, а не по наличию стеков на поле: `clearCount` — достигнутая масса, `clearAll` — `remainingMass === 0`. Победа проверяется после полного разрешения цепи.

### Ящики (только rulesVersion 2)

- Ящик занимает клетку как blocker: туда нельзя поставить магнит, токен не проходит через неё, а ящик не участвует в merge, цели или mass balance.
- После каждой волны clear разрушаются все ящики, соседние по hex-стороне с клеткой каждого очищенного стека этой волны. События `crateDestroyed` идут после событий merge/clear в стабильном порядке клетки; открытая клетка доступна следующим волнам того же действия.
- Разрушение ящика не создаёт и не уничтожает токенную массу. Уровни без ящиков могут продолжать использовать rulesVersion 1.

## 4. Ходы, результат и сравнение

- Ход расходуется только после валидного placement, включая placement без перемещения. Такой ход является legal, но не effective; он расходует лимит. Invalid action не расходует лимит.
- Сначала завершается разрешение действия, затем проверяется победа. Если цель достигнута на последнем разрешённом ходе — это победа. Иначе лимит исчерпан — поражение. Победа имеет приоритет над поражением.
- Если до действия нет ни одного доступного цвета или пустой незаблокированной клетки, сессия проиграна как `no-legal-action`. Пустая клетка обязательна для placement даже если магнит временный.
- Score: `100 × clearedMass + 10 × mergedUnits + 50 × max(0, chainLinks - 1)`, где `mergedUnits` — число единичных токенов сверх одного, поглощённых слияниями за run (учитывается суммарная масса входных стеков минус 1 на merge-компоненту). Score целый и не зависит от wall clock.
- `clearPercent = floor(100 × clearedMass / initialMass)`. Для `clearAll` initialMass обязан быть положительным. Неочищенная масса и blockers не считаются очищенной.
- Challenge сравнивает только одинаковые `puzzleId`, `contentVersion`, `rulesVersion` и mode. Порядок: win > loss; затем score больше; затем ходов меньше; затем активное время меньше; точное равенство — tie. Активное время — целые миллисекунды только в результате, не в simulator state/score; отсчёт приостанавливается на pause/hidden.
- Assisted run записывает неизменяемые `assistedFlags` (hint, undo, extraMove и будущие виды). Результат остаётся видимым, но challenge eligibility — `unassisted-only`: любой флаг исключает его из таблицы/победы над целью. Это не запрещает локальный replay.

### Помощь в забеге (booster policy v1)

- На одну попытку даётся не более одного Undo, одной Hint и одного Extra Move. Новый Retry/reset начинает попытку заново и возвращает эти лимиты; любое получение помощи остаётся в `assistedFlags` до конца именно этой попытки.
- Undo доступен после разрешённого принятого хода, кроме фазы `resolving` и уже достигнутой победы. Он один раз возвращает полный `GameState` непосредственно до последнего принятого Action (позиции и массы фишек, очищенную массу, цепочки, цель, доступный цвет и лимит ходов). Активное время не откатывается. Флаг `undo` не снимается восстановлением состояния.
- Hint разрешён только если текущий GameState в точности совпадает с префиксом авторского `LevelDefinition.solution`. Возвращается следующий Action после проверки через тот же `applyAction`; для отсутствующего решения, завершённого префикса или отличающегося состояния показывается unavailable без подстановки произвольного хода. Перебирается максимум 16 авторских Actions за запрос; асинхронного поиска нет, resolver инвалидируется при reset/load и dispose.
- Extra Move выдаёт ровно один дополнительный ход при конечном положительном лимите в `playing` или после `lost` с причиной `move-limit`, если на поле осталась legal placement. Он недоступен после победы, при `no-legal-action` и unlimited лимите. Ход не начисляет score. Общий grant callback сейчас подключён к `standalone-test`: он явно обозначен в интерфейсе, не запускает и не обещает рекламу. Реальный rewarded provider относится к TASK-0021.
- Loss с доступным Undo/Extra Move считается предварительным: в локальный рекорд он фиксируется при выборе Retry или Home; Undo/Extra Move продолжает попытку без сохранения отменённого terminal результата.

## 5. Чистый контракт модели

Общие поля: `schemaVersion: 1`, `rulesVersion: 1 | 2`. Rules v1 сохраняет исходную семантику; v2 добавляет только ящики. Объекты сериализуются JSON; числа конечные целые, IDs непустые уникальные строки. Не сериализовать `Date`, функции, UI/renderer объекты, порядок свойств незначим.

### LevelDefinition

```json
{
  "schemaVersion": 1, "rulesVersion": 1,
  "puzzleId": "prototype-01", "seed": "seed-01", "contentVersion": 1,
  "geometry": {"kind": "odd-r", "rows": 7, "cols": 7},
  "colors": ["red", "blue", "yellow"],
  "blockedCells": [],
  "crates": [],
  "tokens": [{"tokenId":"t1", "color":"red", "mass":1, "cell":{"col":1,"row":1}}],
  "goal": {"kind":"clearCount", "mass":3},
  "moveLimit": 8,
  "magnetSchedule": [{"options":["red"]}],
  "mode": "campaign"
}
```

`crates` — необязательный массив координат, допустимый только с rulesVersion 2; уровни v1 трактуют его как пустой. `goal.kind` — `clearCount` с положительной целой массой или `clearAll` без mass. `moveLimit` — положительное целое либо `null` (unlimited). `magnetSchedule` не пуст; каждая options содержит уникальные известные цвета. Для ходов за пределами расписания повторяется последняя запись. `mode`: campaign, challenge, daily или prototype. Level не генерируется из seed: seed идентифицирует воспроизведение; контент фиксирован и адресуется вместе с `puzzleId`/`contentVersion`.

### Action

```json
{"type":"placeMagnet","color":"red","cell":{"col":3,"row":3}}
```

### GameState

`{schemaVersion,rulesVersion,puzzleId,contentVersion,seed,turn,remainingMoves,selectedMagnetOptions,tokens,blockedCells,crates,clearedMass,initialMass,mergedUnits,chainLinks,terminal}`. Tokens имеют `tokenId,color,mass,cell`; массивы для сравнения сортируются по ID. `terminal` — null или `{outcome:"win"|"loss",reason}`.

### ResolutionEvent

Каждое событие имеет `{seq,type,turn,wave,...}` с возрастающим seq без пропусков внутри результата. Порядок: `actionAccepted`; по каждой волне `tokenMoved*` (tokenId); затем `stackMerged*` (минимальный tokenId); `stackCleared*`; для v2 затем `crateDestroyed*`; при окончании `goalProgress`; последний `runEnded`, если terminal. Нулевые события не излучаются. Snapshot полного результата после каждого события не обязателен; перемещаемые token IDs и клетки обязательны.

### applyAction / RunResult

`applyAction(state, action) -> {accepted:false, reason, state}` либо `{accepted:true,state,events}`. Входы не мутируются. Один вызов — один ход и полная детерминированная симуляция; RNG и wall clock не читаются.

`RunResult`: `{schemaVersion,rulesVersion,puzzleId,contentVersion,seed,mode,outcome,reason,score,movesUsed,clearPercent,clearedMass,activeTimeMs,assistedFlags,eligibilityVersion:1,eligibleForChallenge}`. Поле времени добавляет владелец сессии при финализации; модель результата его не вычисляет.

## 6. Неизменяемые решения и открытые ограничения

- GDD говорит «one legal step»; выбранные волны до покоя — заметное продуктовое уточнение ради chain reaction и требуют проверки прототипом TASK-0011. Это не физическая симуляция.
- GDD не определяет реализацию route tie-break, очков и assisted challenge; значения выше — правила v1, не утверждение о ранее принятом дизайне.
- UI, анимации, active-time clock, SDK, сеть, сохранения и античит не принадлежат pure simulator. Детерминированный клиентский replay сам по себе не доказывает честность результата.
