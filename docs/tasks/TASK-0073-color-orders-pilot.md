## 4. Требуемое поведение

1. Одна цель пилота: одновременно выполнить два quotas по цветам. Пример A: blue20+coral10; начальная палитра содержит оба. Порядок выполнения свободный. Остальные цвета можно чистить: уменьшают заполнение, но не увеличивают нужную квоту.
2. State хранит orderTargets и collectedByColor; учитывать только units из unitsCleared, каждый ID один раз. UnitMoved/stackSpawned не дают credit. Масса spawnedUnits=remaining+cleared сохраняется; превышение квоты возможно и честно отображается, progress clamp.
3. Победа — все квоты выполнены после resolve, до spawn; выигрыш выше поражения. Если общий cleared велик, но один заказ не выполнен, игра продолжается. Стопки/queue/radii/direct pull/clear10 сохраняются. Генератор не подменяет будущие цвета после выбора игрока.
4. Новый профиль/версия отделён от rulesVersion4. Все старые v4 fixtures и descriptors остаются совместимы со старым поведением. Не переносить номер5 автоматически во все production level data.
5. Три фиксированные доски: одна обучает квотам без лишнего цвета; одна даёт выбор между освобождением и нужным нижним цветом; одна требует подготовительного хода. Layout/seed и targets задаются после принятого темпа, каждый имеет runtime-verified witness. На одном показать две legal альтернативы с разным эффектом на заказы.
6. Два небольших счётчика с иконкой+словом цвета и количеством вместо только общей полосы; источник credit — presentation arrivals из реальных clear events. Reduced выводит тот же итог. Нельзя отчитываться о финальном заказе раньше завершения его collection.
7. Пилот сравнить с обычной целью на сопоставимом preset. Человеческая проверка минимум двух игроков: поняли ли нужные цвета без автора, назвали ли выбор перед ходом, отличили ли бесполезный для квоты сбор от пустого действия. Не обещать уникальность решения/мировую новизну.
