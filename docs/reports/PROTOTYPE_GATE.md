# Проверка прототипа Magnet Sort — протокол

## Статус

Решение: `rework` перед публичным масштабированием, потому что нет human/device evidence по пониманию управления и читаемости pseudo‑2.5D. Пользователь 2026-10-07 разрешил пропустить физические замеры/новых тестеров и продолжить очередь; поэтому TASK-0010/0011 закрыты с waiver. Это решение не означает, что device evidence собраны.

## Что уже подтверждено

- В TASK-0010 есть ровно пять FTUE уровней и три prototype уровня. Unit-проверки проигрывают авторские решения симулятором; browser flow проверяет первый урок, переход к уроку 2, skip, победу/поражение и retry.
- На commit `8ad8554` прошли `pnpm test` (78/78), `pnpm test:browser` (desktop + touch-emulation 390×844) и `pnpm check:full`.
- Эти проверки не являются наблюдением новых игроков, телефонной производительностью или подтверждением тактильного ощущения.
- В предыдущем обзоре пользователь сообщил, что сцена выглядит полностью 2D. Commit `8ad8554` усилил псевдо‑2.5D фасками, тенями и поднятой drop-площадкой. Нужно перепроверить восприятие после обновления страницы; один отзыв не заменяет трёх новых тестеров.

## Краткий протокол наблюдения

### Подготовка

1. Использовать опубликованный Pages build и свежую вкладку без сохранённого состояния; записать commit/build и URL.
2. Набрать трёх новых людей, ранее не знакомых с Magnet Sort. Не считать владельца проекта или автора сборки одним из трёх новых тестеров.
3. Предпочтительный baseline — Pixel 6a, Android 13+, Chrome stable, portrait/touch. Если его нет, записать точную фактическую модель и версию ОС/браузера, не переносить показатели на Pixel 6a.
4. Включить запись экрана только с согласия участника; не записывать имя, аккаунты и личные уведомления.

### Сессия каждого тестера

1. Дать телефон с открытым первым экраном. Сказать только: «Поиграйте и вслух рассказывайте, что вы ожидаете от игры». Не объяснять магниты, drag/tap или правила.
2. Не подсказывать. Записывать время до первого действия, неверные размещения, использование/пропуск hint, завершение каждого из пяти FTUE, переходы, reset/retry и слова/паузы, указывающие на непонимание.
3. После FTUE предложить прототипные уровни 1–3 без объяснения правил. Отметить реакцию на merge/chain, успешные решения и желание повторить.
4. После игры спросить: «Что делает магнит?», «Почему фишки объединились?», «Что было непонятно?», «Хотите сыграть ещё раз? Почему?» Ответы записывать дословно короткими фрагментами без идентификаторов.
5. Измерить полную длительность сессии. Не подгонять её под гипотезу 20–60 секунд.

## Технический замер на том же устройстве

На одном и том же телефоне и одном build записать модель/OS/Chrome, 60 Hz режим, сеть и отключённый DevTools throttling. Очистить cache перед cold load. После одного одинакового прогрева записать 60 секунд прототипного play/retry сценария, затем выполнить 20 одинаковых retry. Сохранить Chrome Performance trace и DevTools memory snapshots до/после.

- p95 frame: целевой бюджет `<16.7 ms` для 60 Hz.
- Input-to-first-feedback: целевой бюджет `150–300 ms` по GDD/архитектуре.
- CPU симуляции и CPU render записывать отдельно; CPU render не называть GPU time.
- Cold-load transfer и heap фиксировать как baseline: проект не задал численный предел веса/памяти.
- После 20 retry проверить устойчивый рост heap/listeners/display resources; проект задаёт отсутствие ухудшения, но не MB-порог.
- Любое измерение через desktop или touch emulation подписать как surrogate и не использовать для закрытия device критериев.

## Решение и дальнейшее использование

Решение по текущему ограниченному evidence — `rework` до публичного масштабирования: пройти тест с тремя новыми игроками и выполнить device measurements, если они станут доступны. Пользователь явно распорядился продолжать задачи независимо от этих пунктов, поэтому начинается авторинг кампании; выводы по удержанию, производительности и реальному phone feel остаются открытыми. При появлении evidence дополнить таблицу наблюдений и пересмотреть gate, не переписывая пропуски как успешные результаты.
